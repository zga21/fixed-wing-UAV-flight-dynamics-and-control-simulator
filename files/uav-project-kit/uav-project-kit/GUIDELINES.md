# GUIDELINES.md

Project handbook. Read this before touching any code. Every task file assumes
you have read this document.

---

## 1. What this project is

A research-grade simulation platform for **nonlinear fixed-wing aircraft
dynamics and autonomous flight control**.

The goal is not "a simulator". The goal is to be able to make one sentence
true, and to have the evidence that backs it:

> Controller B met the predefined tracking, constraint and stability criteria
> in **97.3%** of 10,000 randomised aircraft-and-environment cases
> (95% CI: 96.96–97.61%), versus **78.1%** for the conventional baseline
> controller, on paired scenarios, p < 0.001.

Everything in this repository exists to earn the right to say that sentence.
The simulator is infrastructure. The controllers are the objects of study.
The Monte Carlo campaign is the measurement.

### The core research question

> How can we design a flight-control system that performs well not just for a
> perfect mathematical aircraft, but across realistic uncertainty and
> disturbances?

### The five research questions

| ID | Question | Answered by |
|----|----------|-------------|
| RQ1 | How much does nominal performance deteriorate when aero coefficients, mass properties and environment vary? | Phase 5 degradation table, extended in Phase 9 |
| RQ2 | Does a nonlinear/robust controller meaningfully beat a conventional one across the envelope? | Phase 6, confirmed statistically in Phase 9 |
| RQ3 | Can numerical optimisation improve performance without overfitting? | Phase 7 generalisation gap |
| RQ4 | Can probabilistic models identify low-confidence regions of the envelope? | Phase 8 confidence map |
| RQ5 | What probability of satisfactory closed-loop performance can be demonstrated? | Phase 9 success rate + Wilson interval |

## 2. Scope boundary

**In scope.** Flight dynamics and rigid-body modelling; aerodynamic stability
and control derivatives; trajectory and path tracking; disturbance rejection;
state estimation; actuator and sensor dynamics; nonlinear and robust flight
control; controller optimisation; uncertainty quantification; Monte Carlo
robustness analysis; ML-based model augmentation and residual modelling.

**Out of scope.** Weapons and weapon-system modelling; targeting or target
selection; engagement logic; adversarial pursuit/evasion; terminal attack
guidance; payload delivery. This boundary is deliberate and keeps the research
objective unambiguous. Do not add these.

---

## 3. The build order (non-negotiable)

```
Physics -> Validation -> Baseline control -> Robustness -> Optimisation -> ML
```

Machine learning comes near the **end**, not the beginning. Sophisticated
optimisation or learned models are meaningless if the underlying equations,
coordinate conventions, trim solutions or actuator models are wrong.

Each phase ends with a **gate**: a set of tests that must pass before the next
phase begins. The project does not advance merely because the code executes.

| Phase | Name | Blocked until |
|-------|------|---------------|
| 0 | Freeze the rules | — |
| 1 | Rigid body 6-DOF | Phase 0 documented |
| 2 | Aerodynamics + propulsion | Phase 1 conserves momentum and energy |
| 3 | Trim + linearisation | Phase 2 produces correct force signs |
| 4 | Baseline controller (PID) | Phase 3 gives correct aircraft modes |
| 5 | Sensors, actuators, wind, EKF | Phase 4 flies the perfect aircraft |
| 6 | Robust / nonlinear controller | Phase 5 has degraded Phase 4 measurably |
| 7 | Controller optimisation | Phase 6 beats baseline by hand-tuning |
| 8 | Probabilistic / ML modelling | Phase 7 produced tuned controllers |
| 9 | Monte Carlo campaign | All prior gates green |
| 10 | Report + demonstration site | Phase 9 produced a results database |

## 4. Tech stack

| Layer | Choice | Why |
|-------|--------|-----|
| Language | Python 3.11+ | Fast model iteration, the whole scientific stack |
| Arrays / maths | NumPy | Core numerics |
| Solvers / optimisers | SciPy | `fsolve` for trim, `minimize`, linear algebra |
| Global optimiser | `cma` (CMA-ES) | Noisy, non-convex, gradient-free objective |
| GP regression | scikit-learn `GaussianProcessRegressor` | Phase 8; swap to GPyTorch only if needed |
| Dataframes | pandas | Monte Carlo results analysis |
| Storage | Parquet (pyarrow) for campaigns, JSON for exports | Compact, typed, resumable |
| Plotting | Matplotlib | Every figure generated by a committed script |
| Config | YAML (`pyyaml`) + Pydantic | Typed, validated, version-controlled parameters |
| Testing | pytest | Gates are pytest tests |
| Lint / format | ruff + black | One command, no debates |
| Types | mypy (non-blocking at first) | Catches shape and unit mistakes early |
| Version control | git, from day one | Reproducibility is part of the result |

**Deferred deliberately.**
- **C++** — only after profiling proves Python is the bottleneck. Premature C++
  slows down modelling and verification, which is where the real risk is.
- **JAX** — only if you need autodiff through the dynamics for gradient-based
  tuning. Not required for the main path.
- **PyTorch** — only if the GP proves insufficient in Phase 8.
- **MATLAB/Simulink** — useful as an *independent cross-check* of Phase 3
  linearisation and modes. Do not maintain a second full simulator.

## 6. Important commands

```bash
# --- daily loop -----------------------------------------------------------
make test                  # full test suite
make test-fast             # unit tests only, skips slow gate tests
make gate PHASE=2          # run only the gate tests for one phase
make lint                  # ruff + black --check
make format                # black + ruff --fix
make types                 # mypy src/

# --- simulation -----------------------------------------------------------
python -m uav_sim.cli trim --V 25 --gamma 0
python -m uav_sim.cli modes --V 25          # eigenvalues + named modes
python -m uav_sim.cli fly --scenario config/scenarios/mission_a.yaml \
                          --controller baseline --plot

# --- optimisation (Phase 7) ----------------------------------------------
python -m uav_sim.optimise.run_cmaes --controller baseline --budget 2000
python -m uav_sim.optimise.run_cmaes --controller ndi --budget 2000

# --- Monte Carlo (Phase 9) ------------------------------------------------
python -m uav_sim.montecarlo.campaign --n 10000 --controllers baseline,ndi \
       --workers 8 --out results/mc_v3
python -m uav_sim.analysis.report --campaign results/mc_v3

# --- reproduce everything -------------------------------------------------
make reproduce             # regenerates every figure in the report from results/
```

`make reproduce` working end-to-end on a clean clone is the definition of
"project finished".

## 7. Coding conventions

### Units and angles

- **SI units everywhere internally.** Metres, kilograms, seconds, radians,
  Newtons, Newton-metres.
- **Radians internally, degrees only at the I/O boundary** (config files, CLI
  arguments, plot labels, report text). Convert once, at the edge.
- Any variable holding degrees must be named with a `_deg` suffix. No
  exceptions. `alpha` is radians; `alpha_deg` is degrees.
- Time in seconds. Rates in per-second. No milliseconds anywhere.

### Frames

- Every function that takes or returns a vector must say which frame it is in,
  both in the type name or variable suffix and in the docstring.
- Suffix convention: `_b` = body frame, `_n` = NED inertial frame,
  `_w` = wind frame. `v_b`, `F_b`, `pos_n`, `wind_n`.
- A function that mixes frames without an explicit rotation is a bug.

### Function design

- **Physics functions are pure.** Same inputs, same outputs, no hidden state,
  no globals, no I/O. This is what makes them testable and parallelisable.
- **Stateful objects only where physically justified**: actuators (they have a
  position), filters (they have a covariance), controllers (they have an
  integrator). Everything else is a function.
- Every stateful object exposes `reset()`.
- No module-level mutable state. Ever. It breaks multiprocessing in Phase 9.

### Randomness

- **Never call `np.random.*` directly.** Always pass an explicit
  `np.random.Generator` created from a seed.
- Every object that needs randomness takes `rng` in its constructor.
- One seed per Monte Carlo case derives all randomness for that case, via
  `np.random.default_rng(seed)` and `rng.spawn()` for sub-streams.
- Rationale: Phase 9 is worthless if runs are not bit-reproducible.

### Typing and shapes

- Type-hint every public function.
- Document array shapes in the docstring: `x: (13,)`, `A: (13, 13)`.
- Use `dataclass` (frozen where possible) for structured returns rather than
  returning bare tuples of five things.

### Naming

- Match the mathematical notation from the build guide. `C_m_alpha` in code
  maps to `C_{m_alpha}` in the report. Do not invent new names for known
  aerodynamic derivatives.
- Config keys use the same names as the code fields.

### Magic numbers

- Zero magic numbers in `src/`. Every physical constant comes from config or
  from `constants.py`. If you type `9.81` into a function body, it is a bug.

### Docstrings

Every physics function gets:

```python
def rigid_body_derivatives(x, F_b, M_b, params):
    """
    Nonlinear 6-DOF rigid-body state derivative.

    Implements:
        pdot_n   = R_nb @ v_b
        vdot_b   = F_b/m - omega x v_b
        qdot     = 0.5 * Omega(omega) @ q
        omegadot = I^-1 (M_b - omega x (I omega))

    Args:
        x:      (13,) state [pN pE pD u v w q0 q1 q2 q3 p q r]
        F_b:    (3,) total force in body frame, N, INCLUDING gravity
        M_b:    (3,) total moment in body frame, N.m
        params: AircraftParams

    Returns:
        (13,) state derivative

    Reference: Stevens & Lewis, Aircraft Control and Simulation, 3rd ed., Ch. 1
    """
```

The `Reference:` line matters. Anyone auditing your simulator needs to know
which textbook convention you followed.

## 8. Configuration

- All aircraft parameters, limits, uncertainty distributions and scenarios live
  in `config/*.yaml`, version controlled.
- Config files are **versioned by filename**: `aircraft_v1.yaml`,
  `aircraft_v2.yaml`. Never edit a config that results have already been
  generated from — create the next version. Old results must stay explicable.
- Every results file records the config hash it was produced with.
- Config is loaded once into a frozen Pydantic model and passed down. No
  component reads YAML itself.

## 9. Testing philosophy

Three tiers:

| Tier | Marker | Runtime | Purpose |
|------|--------|---------|---------|
| Unit | (none) | < 1 s each | One function, one property |
| Gate | `@pytest.mark.gate` | seconds to minutes | Phase exit criteria |
| Campaign | `@pytest.mark.slow` | minutes+ | Monte Carlo smoke tests |

Rules:

- **Gate tests are written before the phase is declared done**, and they live
  in `tests/gates/test_phase_N.py`.
- Every gate test has a **numeric tolerance written into the test**, not a
  visual check. "The plot looks right" is not a test.
- A physics test asserts a *property* (energy conserved, sign negative,
  symmetry exact), not a golden number copied from a previous run.
- When you find a bug, write the failing test first, then fix it.

Why this matters: a flight simulator can contain 300 correct equations and one
wrong minus sign, and it will still run, still produce plots, and still be
completely worthless.

## 10. Results and artefacts

```
results/                       # gitignored, regenerable
  mc_v3/
    cases.parquet              # one row per Monte Carlo case
    manifest.json              # git commit, config hash, timestamp, N
    trajectories/              # a handful of saved time histories
figures/                       # gitignored, regenerated by scripts/
```

- Every results row records: `seed`, `controller`, `git_commit`,
  `config_hash`, all sampled parameters, all metrics, `success` flag.
- A result you cannot trace back to a code version is not evidence. If
  `git status` is dirty when a campaign starts, the campaign records
  `dirty: true` and the result is for exploration only, never for the report.
- Nothing in `results/` or `figures/` is committed. Everything in them must be
  regenerable by `make reproduce`.

## 12. How to work through a task

1. Read the task file in `tasks/`.
2. Read the "Background" and any referenced docs before writing code.
3. Create the files listed under "Files".
4. Write the tests listed under "Acceptance criteria" first if you can.
5. Implement.
6. Run `make test` and `make lint`.
7. Tick the task in `TASKS.md`, commit, open the next task.

If a task turns out to be bigger than its estimate, **split it** and add the
new task files rather than letting one task sprawl. Small tasks are the point.

## 13. Common traps

| Trap | Symptom | Prevention |
|------|---------|-----------|
| Missing `omega x (I omega)` term | Aircraft never tumbles; angular momentum drifts | Phase 1 gate test 4 |
| Gravity sign wrong | Aircraft falls upward, or trim needs negative lift | Phase 1 gate test 1 |
| `p_D` treated as altitude | Altitude hold drives the aircraft into the ground | Name it `p_D`, compute `h = -p_D` in one place only |
| `C_m_alpha` positive | Pitch diverges; controller blamed | Phase 2 gate test 2 |
| Degrees leaking into physics | Results wrong by a factor of 57.3 | `_deg` suffix rule |
| Using ground velocity for aero | Wind has no effect on lift | Phase 5: all aero uses `v_air`, never `v_b` |
| Global RNG | Monte Carlo not reproducible | Always pass `rng` |
| Actuator ops in wrong order | Rate limit does nothing | Lag, then rate limit, then saturation |
| NDI inversion at low `q_bar` | NaNs everywhere | Clamp `q_bar`, check `cond(G)` |
| Tuning on the test set | Great numbers, no generalisation | Disjoint train/val scenario sets |
| Unpaired statistical test | Loses most of the statistical power | McNemar on paired seeds |

## 14. Glossary

| Term | Meaning |
|------|---------|
| 6-DOF | Six degrees of freedom: three translations, three rotations |
| NED | North-East-Down inertial frame. **Down is positive**, so `h = -p_D` |
| Body frame | x out the nose, y out the right wing, z down through the belly |
| Trim | The exact state and control input for steady, unaccelerated flight |
| Linearisation | Local linear model `dx = A dx + B du` valid near a trim point |
| Short period | Fast pitch oscillation, ~3–10 rad/s |
| Phugoid | Slow speed/altitude exchange oscillation, ~0.1–0.5 rad/s |
| Dutch roll | Coupled yaw-roll oscillation |
| Aleatoric uncertainty | Genuinely random (gusts). Irreducible |
| Epistemic uncertainty | Things you don't know (true `C_m_alpha`). Reducible with data |
| NDI | Nonlinear Dynamic Inversion: cancel the plant, impose desired dynamics |
| TECS | Total Energy Control System: throttle sets total energy, elevator sets its distribution |
| Gate | Test set that must pass before the next phase starts |
