## Background

The report is the deliverable that survives. Code rots, links break, but a
well-written technical report explaining what was asked, how it was answered, and
what the limitations are remains useful and readable for years.

It follows the structure in the Project Definition, section 22. Two rules govern
it: every figure is generated by a committed script, and the limitations section
is written honestly.

## Section 14 — Limitations

Write this honestly and early. At minimum:

- Rigid-body assumption; no aeroelasticity
- Coefficient-based aerodynamics valid only within the stated envelope
- The "truth" model in Phase 8 is itself a model, not measured data
- Uncertainty distributions chosen by engineering judgement, not measured
- Flat, non-rotating Earth
- No sensor failure modes or fault-tolerant control
- Simulation only; no hardware-in-the-loop or flight validation
- Single airframe, single class of manoeuvre

Stating these clearly makes the rest of the work *more* credible, not less. A
reviewer who spots an unstated limitation stops trusting everything; one who sees
you identified it first trusts the rest.

## Section 15 — Future work

The natural extensions, in order of value:

1. Validate against published wind-tunnel or flight-test data for a real airframe
2. Hardware-in-the-loop: run the controller on a real flight-controller board
   fed by the simulator
3. Fault-tolerant control: actuator failures, sensor dropouts
4. Adaptive or learning control using the GP uncertainty online
5. Flight testing on a physical airframe, using the logs to identify the true
   derivatives and close the loop on the uncertainty model

## Acceptance criteria

- [ ] All sections present
- [ ] Every figure generated by a committed script; none inserted by hand
- [ ] All five research questions explicitly answered, each with a number
- [ ] The headline sentence appears in the abstract and the conclusion, with
      identical numbers
- [ ] Limitations section written honestly, at least eight items
- [ ] Every parameter value cited
- [ ] `make report` builds the PDF from source
- [ ] Someone else has read it and can state what the project concluded
- [ ] `make reproduce` on a clean clone regenerates every number in it

## Notes

Write the abstract last, and write it as four sentences: what problem, what you
built, what you measured, what you found. If you cannot compress it to four
sentences, the project's story is not yet clear — and that is worth fixing before
you write forty pages around it.
