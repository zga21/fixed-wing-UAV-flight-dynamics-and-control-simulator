## Background

This is where controller-comparison studies quietly cheat, usually without
meaning to. The new controller gets three weeks of loving attention; the baseline
got an afternoon. The new controller is tested on scenarios chosen after seeing
what it is good at. The two run with different random seeds and the difference is
partly luck.

This task builds a harness that makes cheating structurally difficult, and it
does so **before** you have seen any comparison results — which is the only time
you can design it honestly.

```python
def compare_controllers(controllers: dict[str, Controller],
                        scenarios: list[Scenario],
                        seeds: list[int],
                        plant_factory, cfg) -> pd.DataFrame:
    """
    Every controller sees:
      - the SAME scenario list
      - the SAME seeds (so the same turbulence realisation, the same sensor
        noise sequence, the same initial conditions)
      - the SAME plant, actuators, sensors and EKF instances-by-construction
      - the SAME metrics

    Returns a long-format frame: one row per (controller, scenario, seed).

    The pairing by seed is what makes McNemar's test valid in Phase 9. Do not
    let controllers run on independently drawn seeds.
    """

def assert_fair_comparison(results: pd.DataFrame) -> None:
    """
    Raises if:
      - controllers were run on different seed sets
      - controllers were run on different scenario sets
      - any controller has missing runs
      - the git commit differs between controller runs
    Called automatically at the end of compare_controllers.
    """
```

Write `docs/fairness_protocol.md` stating the four rules from the build guide:
same estimator, same hardware models, same scenarios and seeds, comparable tuning
effort. Commit it now, before the results exist. It reads very differently in
review when the git history shows it predates the numbers.

## Acceptance criteria

- [ ] Both controllers run on identical `(scenario, seed)` pairs
- [ ] `assert_fair_comparison` raises on a deliberately unfair input — test this
- [ ] Results frame includes controller name, scenario, seed, git commit, config
      hash, and every metric
- [ ] A paired difference per `(scenario, seed)` can be computed directly from
      the frame
- [ ] A summary table and a paired-difference plot are generated
- [ ] Runs in parallel with the same results as serial — assert bit-identical

## Notes

The tuning-effort rule is the one that cannot be enforced by code, and it is the
one most likely to be violated. The mitigation is Phase 7: both controllers go
through the same optimiser with the same evaluation budget. Until then, treat any
Phase 6 comparison as provisional and say so in the report.

If NDI does not beat the tuned PID once both are optimised, that is a legitimate
and publishable result. Report it. A study that honestly concludes "the added
complexity did not pay off for this aircraft and envelope" is far more valuable
than one that quietly weakens the baseline until the answer comes out right.
