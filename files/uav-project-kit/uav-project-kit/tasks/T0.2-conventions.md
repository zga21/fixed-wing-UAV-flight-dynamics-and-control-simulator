## Background

Before two people play a board game they agree the rules. If you skip that and
start playing, you spend three hours arguing about whether someone cheated. In
this project that argument is called debugging, and it can eat a month.

This task produces **zero executable code**. It produces the single document
that every equation in the project refers back to. A flight simulator can
contain 300 correct equations and one wrong minus sign and still run, still
produce plots, and still be completely worthless. This document is how you
avoid that.

The specific decisions matter less than the fact that they are written down and
never silently changed.

## What to decide and write down

Work through all thirteen sections of the template. The ones that most commonly
get skipped, and that cause the most damage later:

**1. Altitude sign.** NED means positive `p_D` is downward, so `h = -p_D`.
Write it on the first line. Decide now that `h` is computed in exactly one
place in the codebase.

**2. Quaternion convention.** Scalar-first `[q0, q1, q2, q3]`, body-to-NED,
unit norm. Half the textbooks use scalar-last; if you mix them, your rotation
matrix will be silently transposed and your aircraft will fly sideways.

**3. Control sign convention.** Pick what positive elevator *does*. Every
aerodynamic derivative sign in Phase 2 follows from this choice, and the Phase 2
gate tests assert those signs. If you change this later, those tests must change
too.

**4. Aircraft parameters with sources.** Fill the table with real numbers and
cite each one in `sources.bib`.

> **Strong recommendation.** Rather than inventing plausible values, base the
> aircraft on a published airframe with measured aerodynamic derivatives — for
> example an aircraft documented in a NASA technical report, or the Aerosonde
> parameters published alongside Beard & McLain's textbook. This costs you an
> afternoon of reading and buys you something valuable: in Phase 3 you can
> compare your computed modes against *measured* values rather than against a
> plausible range. That upgrade turns "my equations run" into "my model
> reproduces measured aircraft behaviour", which is the single biggest
> credibility gain available in the whole project.

**5. Flight envelope.** The bounds outside which you do not claim the model is
valid. Phase 9 counts excursions beyond these as constraint violations, so
choosing them loosely will hide real failures.

- [ ] The document states, explicitly, all five of: frames, quaternion

## Notes

Treat this document as frozen the moment Phase 1 starts. If you genuinely need
to change something, create `conventions_v2.md`, note what changed and why, and
re-run every gate that the change touches. Silently editing it makes all
previous results unexplainable.
