## Background

CMA-ES is the right tool here. It needs no gradients, tolerates a noisy and
non-smooth objective, and adapts its own search distribution as it learns the
shape of the problem. A flight simulator with saturation, rate limits and
turbulence produces exactly that kind of objective.

The practical work is mostly plumbing: parallelise the population evaluation,
checkpoint so a crash at hour six is not fatal, and log enough that the run is
explicable afterwards.

## What to implement

```python
@dataclass
class TuningResult:
    k_best: np.ndarray
    J_train: float
    J_val: float
    history: pd.DataFrame        # generation, best, mean, sigma, term breakdown
    n_evaluations: int
    wall_time: float
    git_commit: str
    config_hash: str

def tune(controller_factory, k0, bounds, train_set, val_set,
         sigma0=0.3, budget=2000, n_workers=8,
         checkpoint_path=None, seed=42) -> TuningResult:
    """
    CMA-ES with:
      - population evaluated in parallel (one process per candidate)
      - checkpoint every generation, resumable
      - validation score computed every 10 generations for the overfitting
        curve, but NEVER used to steer the search
      - early stop when the best has not improved for 30 generations
    """
```

**Normalise the search space.** CMA-ES uses one `sigma0` for all dimensions, so
gains spanning different orders of magnitude will search badly. Map every gain to
`[0, 1]` over its bounds, optimise there, and unmap when constructing the
controller. This one detail often makes the difference between converging and not.

Population size defaults to `4 + 3*ln(n)`; with 12–20 gains that is 12–17
candidates per generation, which parallelises neatly across 8 cores.

## Acceptance criteria

- [ ] `J_best` decreases monotonically in the best-so-far sense
- [ ] Converges (flattens) before the budget is exhausted — if it does not,
      the budget is too small or the search space is badly scaled
- [ ] Tuned gains beat the initial gains by a clear margin on the training set
- [ ] Parallel and serial runs give the same result with the same seed
- [ ] Checkpoint/resume produces the same result as an uninterrupted run
- [ ] The validation curve is recorded but demonstrably never influences the
      search — verify by checking the search history is identical with
      validation evaluation disabled
- [ ] `history` is saved to disk with the git commit and config hash
- [ ] The optimiser respects the bounds; no candidate violates them

## Notes

Watch the convergence plot rather than just the final number. If `sigma`
collapses within a few generations, the objective is probably dominated by
`FAILURE_COST` — most candidates are diverging, so CMA-ES sees a flat landscape
with a cliff and converges to the edge of feasibility. The fix is a better `k0`
and tighter bounds, so that most of the initial population actually flies.
