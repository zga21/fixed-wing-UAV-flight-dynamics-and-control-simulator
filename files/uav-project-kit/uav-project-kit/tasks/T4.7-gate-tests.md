## Background

The gate here has an extra job beyond testing. It produces the **baseline
record**: the performance of a competent conventional controller on a perfect
aircraft. Every later number in the project is measured against it.

Store it as a committed file, not as a number in someone's notebook.

## Files

| Action | Path | Purpose |
|--------|------|---------|
| create | `tests/gates/test_phase_4.py` | The gate |
| create | `docs/baseline_record.json` | The committed reference numbers |
| create | `scripts/record_baseline.py` | Regenerates it |

## What to implement

```python
@pytest.mark.gate
def test_step_responses_meet_spec(baseline, plant):
    """Roll, pitch, altitude and airspeed steps against the T4.3-T4.5 targets."""

@pytest.mark.gate
def test_full_mission_succeeds(baseline, plant):
    """mission_a completes with success=True and no envelope violations."""

@pytest.mark.gate
def test_loop_frequency_separation(baseline):
    """Each outer loop is 3-5x slower than the loop inside it."""

@pytest.mark.gate
def test_envelope_coverage(baseline, plant):
    """
    The same gain set flies missions at V=18, 25 and 35 m/s.

    If it does not, that is a legitimate finding, not a failure -- record the
    degradation, note gain scheduling as the conventional remedy, and carry it
    into the RQ2 discussion. Do not silently re-tune per airspeed and present
    that as one controller.
    """

@pytest.mark.gate
def test_baseline_record_is_current(baseline, plant):
    """Re-running reproduces docs/baseline_record.json within 1%."""
```

`docs/baseline_record.json` contains, for each scenario: every metric, the gain
set used, the git commit, the config hash, and the date.
