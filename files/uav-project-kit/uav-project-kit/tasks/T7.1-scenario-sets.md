## Background

You are about to let a computer try thousands of gain combinations. It will find
whatever makes the number go down — including gains that exploit quirks of the
specific scenarios you tuned on and generalise to nothing.

This is the same problem as a student memorising last year's exam paper. The
remedy is the same: keep a set of questions the tuner never sees.

Building the split **before** writing the objective function is deliberate. If
you build it afterwards you will be tempted to move a scenario across when
results disappoint.

Keep the training set small (40). A large training set makes overfitting less
likely but each objective evaluation proportionally more expensive, and CMA-ES
needs thousands of evaluations. 40 scenarios × 60 s at ~1 s each is around
40 seconds per evaluation, which is the right order for a few thousand
evaluations across 8 cores overnight.

## Acceptance criteria

- [ ] Sets are disjoint — verified by seed and by scenario id
- [ ] Both drawn from the same distribution: compare marginal histograms of wind
      speed, turbulence intensity and initial airspeed; a KS test should not
      reject
- [ ] Regenerating from `master_seed` reproduces both sets exactly
- [ ] Committed as YAML so the exact scenarios are in version control, not
      regenerated implicitly at run time
- [ ] `assert_disjoint` raises on a deliberately overlapping pair
- [ ] Loading is fast — this happens on every optimiser evaluation

## Notes

Commit the generated YAML rather than only the generator. Six months later,
"regenerate with seed 20260101" is a promise that a library upgrade can silently
break; a committed file is a fact.
