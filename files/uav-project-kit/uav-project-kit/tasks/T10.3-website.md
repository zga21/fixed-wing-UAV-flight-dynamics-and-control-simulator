## Background

The website exists to let someone understand the project in five minutes without
reading a 60-page report, and to let a reader *interact* with results rather than
looking at static plots.

One architectural rule governs everything here: **the website is a renderer, not
a second simulator.** Do not reimplement flight dynamics in JavaScript. Python
writes static JSON; the page loads it and draws it. This means no backend, no
server cost, free hosting on GitHub Pages, and — most importantly — the site can
never disagree with the report, because both read the same exported files.

Build it now, at the end, not earlier. Building it before results exist means
designing a UI for data you do not have, which is exactly the feature creep the
project definition warns about.

## Page structure

In the order a reader needs it — this ordering is the design:

1. **The question.** One paragraph, plain English. What problem, why it matters.
   No equations above the fold.
2. **The aircraft and the model.** Geometry, the coefficient structure, what is
   assumed and what is not.
3. **Proof the model is correct.** Trim convergence, the mode table against
   expected ranges, open-loop response, linear-versus-nonlinear agreement.
   *Most portfolio projects skip this section entirely. It is the one an
   engineer will read first, and putting it third signals that you know that.*
4. **Baseline versus advanced.** Both trajectories on one plot, with a toggle for
   wind and turbulence so the reader watches the gap open up.
5. **The uncertainty.** Monte Carlo histogram with a slider to scrub through
   individual cases and see the matching trajectory. Plus the GP confidence map.
6. **The headline number.** Success rates with confidence intervals, the McNemar
   result, stated plainly.
7. **How to reproduce it.** Link to the repo, the commit hash, and the one
   command.

## Implementation

Plain HTML with a plotting library (Plotly or Chart.js) is entirely sufficient. A
framework is not needed for seven static sections and three interactive widgets.

The one thing worth extra effort is a **3D trajectory playback** for section 4,
using three.js. A flight path is genuinely spatial and a 2D plot undersells it —
this is the single interaction that makes the project feel real to a viewer.

```javascript
// Everything is static. No API, no server, no computation in the browser.
const data = await fetch('data/mc_ndi_v3.json').then(r => r.json());
const traj = await fetch('data/traj_worst.json').then(r => r.json());
```

## Acceptance criteria

- [ ] Loads and works with `file://` — no server needed for local viewing
- [ ] Every number on the page comes from `data/*.json`, never hard-coded
- [ ] The Monte Carlo slider scrubs across at least 100 exported cases
- [ ] 3D trajectory playback works, with a play/pause control
- [ ] The wind toggle shows a visible, real difference between the two controllers
- [ ] Mobile-readable — someone will open it on a phone
- [ ] Total page weight under ~5 MB
- [ ] Deploys automatically on push to `main`
- [ ] A visitor with no aerospace background can read section 1 and understand
      what the project does. Test this on an actual person
- [ ] The commit hash on the page matches the commit that produced the data

## Notes

Resist the temptation to make the site a simulator. Running the physics in WASM
is a fun idea and it is a different project; it would also mean two
implementations that can silently diverge, which is precisely what the
architecture here avoids.

Section 3 is the differentiator. Nearly every UAV control project on the internet
shows a controller tracking a reference. Almost none shows eigenvalues compared
against expected aircraft modes, or a linear model agreeing with a nonlinear one
at small signal and diverging at large. That section is the evidence that you
built something correct rather than merely something that runs.
