## Background

**This is the most important gate in the project.**

Phases 1 and 2 checked that the code obeys physics. This gate checks that the
code obeys *aeronautics* — that what you have built behaves like an aircraft, not
merely like a rigid body with forces on it.

Passing this gate is the evidence you will cite in the report when someone asks
why they should believe any of your later results. It is the section of the
website that an engineer will read first.

## What to implement

```python
@pytest.mark.gate
def test_trim_converges_across_envelope(cfg, plant):
    """9 grid points, residual < 1e-10 at every one."""

@pytest.mark.gate
def test_trim_is_physically_sensible(cfg, plant):
    """alpha rises as V falls; delta_t rises with climb angle."""

@pytest.mark.gate
def test_trim_actually_holds(cfg, plant):
    """
    Fly from trim with controls frozen for 60 s.
    Altitude within 1 m, airspeed within 0.1 m/s.
    The definitive test that the trim point is real.
    """

@pytest.mark.gate
def test_all_five_modes_present_and_plausible(cfg, plant):
    """Short period, phugoid, dutch roll, roll subsidence, spiral --
    all present, all inside published ranges for this class of aircraft."""

@pytest.mark.gate
def test_linear_matches_nonlinear_small_signal(cfg, plant):
    """
    0.5 deg elevator doublet, 5 s, linear model vs full nonlinear simulator.
    Trajectories agree within 2%.
    """

@pytest.mark.gate
def test_linear_diverges_from_nonlinear_large_signal(cfg, plant):
    """
    15 deg doublet: the two MUST diverge by more than 10%.

    This is not a formality. It proves the linearisation is genuinely local,
    and it is the empirical justification for building a nonlinear controller
    in Phase 6. Without this test, RQ2 has no motivation.
    """
```

## Notes

Do not start Phase 4 with any of these failing or "explained away". A controller
built on a model with a wrong mode will look like a controller problem for as
long as you are willing to keep looking, and there is no bottom to that.

When this gate is green, write two paragraphs in `docs/` describing what you
verified and how. That text goes almost verbatim into the report's verification
section, and writing it while the work is fresh is much easier than
reconstructing it in month nine.
