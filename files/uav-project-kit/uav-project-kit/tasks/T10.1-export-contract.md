## Background

The report and the website must never disagree with each other. The way to
guarantee that is for both to read the **same** exported files, generated once
from the results database.

Define the schema first, then build both consumers against it. Doing it the other
way round produces a website that quietly displays a stale number.

The schema, from the build guide:

```json
{
  "schema_version": "1.0",
  "experiment_id": "mc_ndi_v3",
  "git_commit": "a3f91c2",
  "config_hash": "8d21ee",
  "generated_utc": "2026-09-14T11:02:33Z",
  "controller": "ndi_tuned",
  "n_cases": 10000,
  "success_rate": 0.973,
  "ci95": [0.9696, 0.9761],
  "metrics": {
    "rmse_h": {"median": 1.82, "p95": 4.11, "p99": 5.94, "worst": 9.20},
    "rmse_V": {"median": 0.41, "p95": 0.98, "p99": 1.37, "worst": 2.85}
  },
  "comparison": {
    "baseline": "pid_tuned",
    "mcnemar_chi2": 1842.3,
    "p_value": 1.2e-40,
    "discordant_b": 47,
    "discordant_c": 1889
  },
  "trajectories": ["traj_median.json", "traj_p95.json", "traj_worst.json"]
}
```

Trajectory files are decimated to ~20 Hz and contain only what a plot needs:
time, position, Euler angles, airspeed, commands and actual controls. A full-rate
13-state history is megabytes and no viewer needs it.

## Acceptance criteria

- [ ] `docs/export_schema.md` documents every field with type and units
- [ ] Export is deterministic from a campaign directory
- [ ] All floats rounded sensibly — no 17-significant-figure noise in the JSON
- [ ] Every file carries `git_commit` and `config_hash`
- [ ] A schema validation test exists and runs in CI
- [ ] Trajectory files are under ~200 kB each
- [ ] `schema_version` present, so consumers can detect a mismatch

## Notes

Ideally, define this schema back in Phase 0 and have `run_case` populate it from
the start. Doing it here works, but doing it early shapes the metrics code well
and makes the website nearly free at the end. If you are reading this before
Phase 9, go and write the schema now.
